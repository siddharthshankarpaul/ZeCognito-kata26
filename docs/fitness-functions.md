## Architecture Fitness Functions

[README §13](../README.md#13-cicd) and the [CI/CD pipeline diagram](warden-cicd-pipeline.md) describe fitness functions in prose: the build fails if the two-plane separation is ever violated. This page pulls every concrete threshold already decided across the platform ADRs into one scannable table, so "fitness functions" isn't just a claim, it's a list a judge (or an engineer) can check against. Nothing here is a new decision, every row already exists in the ADR it links to.

| Fitness function | Threshold | Automated or Monitored | Where enforced |
|---|---|---|---|
| Plane separation contract test | A build fails if any advisory/AI service reaches the transactional plane without going through the Deterministic Decision Gate. | Automated, CI | [platform/ADR-003](adrs/platform/ADR-003-two-plane-safety-model.md), [warden-cicd-pipeline.md](warden-cicd-pipeline.md) |
| Golden-set eval gate | A candidate prompt/model/threshold change must be no worse than the live version, inside a tolerance band, across seven blocking layers ending in a zero-tolerance red-team suite. | Automated, release gate | [platform/ADR-AI-002](adrs/platform/ADR-AI-002-validation-and-verification.md) |
| Runtime guardrails | Every request's schema, citations, and blocklist are checked; two failures in a row trigger the no-model fallback rather than a silent bad answer. | Automated, runtime, every request | [platform/ADR-AI-002](adrs/platform/ADR-AI-002-validation-and-verification.md) |
| Canary fingerprint check | The same canary prompts run daily against every provider; a changed fingerprint freezes promotion and triggers a full eval rerun. | Automated, scheduled | [platform/ADR-AI-003](adrs/platform/ADR-AI-003-production-monitoring.md) |
| Calibration gate | A new per-zone calibration table is only promoted if its expected calibration error beats the live table's; otherwise it's rejected outright. | Automated, release gate | [platform/ADR-AI-003](adrs/platform/ADR-AI-003-production-monitoring.md) |
| Forecast skill vs naive baseline | A footfall/queue forecast must beat a naive baseline before it ships, and stays under the same comparison once live. | Automated (ship gate) + Monitored (production) | [footfall_and_popularity/001](adrs/footfall_and_popularity/001-adr-crowd-and-popularity-analytics.md) |
| MQTT buffer depth & duplicate rate | Per-gate buffer depth (backlog during an outage) and duplicate rate at the reconciliation layer are tracked; an abnormal trend raises an alert. | Monitored, production | [platform/ADR-001](adrs/platform/ADR-001-store-and-forward-mqtt%20.md) |
| Deny-list staleness tag | Every admission during a stale deny-list window is tagged `unverified-revocation` and logged for review, rather than silently trusted or blocked. | Monitored, production | [ticketing_and_access_control/002](adrs/ticketing_and_access_control/002-adr-revocation-deny-list.md) |
| Spend-ceiling behaviour by tier | At Augur's spend ceiling, welfare calls keep escalating and raise an alert, advisory calls stop escalating, engagement calls degrade, never a silent overspend or a silent outage. | Automated, runtime control | [platform/ADR-AI-001](adrs/platform/ADR-AI-001-provider-and-model-portability.md) |
| Quarterly resilience drills | Provider failover, the kill switch, a fallback usability review, and shadow-job liveness are drilled four times a quarter; a drill that doesn't run counts as a failed drill, not a skipped one. | Monitored, quarterly, pass/fail recorded | [platform/ADR-AI-003](adrs/platform/ADR-AI-003-production-monitoring.md) |
| Raw-vs-derived read contract | A contract test fails the build if an eval, backtest, or the monthly review reads from the AI-derived output store instead of the raw event store. | Automated, CI | [platform/ADR-009](adrs/platform/ADR-009-raw-and-ai-derived-data-separation.md) |
| Ticket capacity check constraint | A capacity-limited slot's remaining count can never go negative; enforced by the database itself, not application code. | Automated, database constraint | [ticketing_and_access_control/004](adrs/ticketing_and_access_control/004-adr-ticket-capacity-and-oversell-prevention.md) |

**Reading the two categories:** *Automated* means the pipeline or a runtime check blocks the change or the request by itself, no human has to notice. *Monitored* means the signal is tracked and alerts a named responder, but the response (investigate, roll back, retrain) is a human decision, not a machine one. This split mirrors the guardrails-vs-evals split in [platform/ADR-AI-002](adrs/platform/ADR-AI-002-validation-and-verification.md): fast, automated checks catch what's wrong on a single occurrence, slower monitored ones catch what only shows up over volume.
